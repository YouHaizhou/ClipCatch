## 1. DNS TTL 缓存 → 搜索结果短期缓存

**知识来源**：DNS 递归查询中每层响应带有 TTL 值，调用方在 TTL 期间内直接复用缓存，不重新请求。缓存空间满时配合 LRU（Least Recently Used）淘汰策略管理条目。

**项目映射**：
- 当前 `search_service.py` 每次搜索都实时请求 Serper / YouTube Data API
- 同一关键词在短时间内（如 5 分钟）多次搜索会重复消耗 API 配额
- TTL 思路：在内存中维护一个 `{query+platform: (results, expire_ts)}` 的字典，TTL = 300s
- LRU 思路：限制缓存最多 100 条记录，满时淘汰最久未访问的条目

**实现参考**：
```python
from functools import lru_cache
import time

# 简单版：用 dict + TTL 手动管理
_search_cache: dict[str, tuple[list, float]] = {}  # key -> (results, expire_ts)
_CACHE_TTL = 300  # 5 分钟
_CACHE_MAX = 100

def _cache_get(key: str) -> list | None:
    if key in _search_cache:
        results, expire_ts = _search_cache[key]
        if time.time() < expire_ts:
            return results
        del _search_cache[key]
    return None

def _cache_set(key: str, results: list):
    if len(_search_cache) >= _CACHE_MAX:
        # LRU 淘汰：删除最旧的条目（简化版，按插入顺序）
        oldest = next(iter(_search_cache))
        del _search_cache[oldest]
    _search_cache[key] = (results, time.time() + _CACHE_TTL)
```

**优先级**：低。API 配额（Serper 每日免费额度、YouTube Data API 10000次/天）在当前用量下不是瓶颈，但如果未来支持多用户或高频使用场景，此优化价值显著。

## 2. TCP 滑动窗口 → 批量下载并发窗口控制

**知识来源**：TCP 滑动窗口允许发送方在等待 ACK 前连续发送多个数据段，窗口大小动态调整，防止接收方被淹没（流量控制）。

**项目映射**：
- 当前下载队列（`download_service.py`）没有并发窗口限制
- 用户选择多个视频下载时，可能同时启动大量 yt-dlp 进程，占满带宽或触发平台限速
- 滑动窗口思路：设定最大并发下载数（窗口大小 = N，默认 2-3），队列中的任务等待窗口滑动后才启动

**实现参考**：
```python
import asyncio
_download_semaphore = asyncio.Semaphore(3)  # 最大并发下载数

async def _download_with_limit(task):
    async with _download_semaphore:
        await _do_download(task)
```

**优先级**：中。当用户有批量下载需求时（对应 PROJECT_OVERVIEW 后续优化方向「批量下载和分析」），此机制是前提基础设施。

## 3. SYN Flood 防护思路 → API Key 测试接口防滥用

**知识来源**：SYN Flood 攻击通过大量半连接耗尽服务端资源。防御手段 SYN Cookie 的核心思路是：在确认对方是合法请求前，不分配真正的资源。

**项目映射**：
- 当前设置页的「测试连接」按钮直接调用 `/api/settings/test-connection`
- 恶意或误操作下可能大量点击，每次都真实发起 LLM API 调用，消耗配额
- SYN Cookie 思路：对同一 API Key 的测试请求做频率限制（如 10秒内最多3次），超出后返回 429 而不发起真实请求

**实现参考**：
```python
from collections import defaultdict
import time

_test_rate: dict[str, list[float]] = defaultdict(list)  # key_hash -> [timestamps]

def _check_rate_limit(key_hash: str, window=10, max_calls=3) -> bool:
    now = time.time()
    calls = [t for t in _test_rate[key_hash] if now - t < window]
    _test_rate[key_hash] = calls
    if len(calls) >= max_calls:
        return False
    _test_rate[key_hash].append(now)
    return True
```

**优先级**：低。当前是单用户桌面应用，滥用风险极低；若未来支持多用户或云端部署则需要。

## 4. OSPF DR/BDR 选举 → LLM 提供商动态优先级

**知识来源**：OSPF 在多路访问网络中选举 DR（指定路由器），规则是优先级最高者胜出，相同则 Router-ID 最大者胜出。DR 负责统一收集和泛洪 LSA，避免 O(n²) 的全连接开销。

**项目映射**：
- 当前 `llm_service.py` 的 Resilient Gateway 使用**静态优先级**（Groq → DeepSeek → OpenAI）
- OSPF DR 选举思路：根据**运行时成功率 + 延迟**动态调整 LLM 提供商优先级
- 某个提供商连续成功且延迟低 → 动态晋升为首选（类比 Router-ID 大优先）
- 某个提供商断路器打开 → 临时降级（类比优先级设为 0，不参选）

**实现参考**：维护每个提供商的 `success_count` / `avg_latency_ms` 滚动窗口统计，每 5 分钟重新排序优先级列表。

**优先级**：低。静态优先级对当前场景已足够，动态选举增加复杂度但收益有限，除非 LLM 提供商数量扩展到 5 个以上。

## 5. BGP AS_PATH 追溯 → 请求链路日志

**知识来源**：BGP 用 AS_PATH 属性记录路由经过的所有 AS，既用于防环也用于追溯路径。

**项目映射**：
- 当前 AI 分析失败时，前端只能看到最终错误信息，无法知道经过了哪些 LLM 提供商降级
- AS_PATH 思路：在 SSE 事件中追加 `provider_path` 字段，记录本次请求尝试的提供商序列
- 例如：`provider_path: ["Groq(failed: timeout)", "DeepSeek(ok)"]`
- 用户在 AI 工作台可看到「使用 DeepSeek 生成（Groq 超时降级）」的提示

**优先级**：中。对用户排障体验有明显帮助，且实现成本低（在现有 SSE 事件结构上增加一个字段）。这个点值得在下一轮优化中考虑。
